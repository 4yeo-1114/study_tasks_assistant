## 简历写作规格（2026-10-14 起，按用户提供的优秀简历样例提炼）

每条项目亮点固定四要素，缺实测数据不写：

1. **定位/问题**：这条优化解决什么场景（如"文档入库后检索慢"）。
2. **做法**：具体技术组合（如"关键词 SQL + pgvector + RRF"），不堆名词。
3. **实测结果**：指标名 + 基线对比 + 数据集规模 + 测量环境（如"80 条冻结测试集上 Recall@5 从 62% 提升到 84%；1 万 chunk 实验库 P95 从 220ms 降至 95ms"）。合成数据/离线替身必须标注。
4. **范围/边界**：一句话限定（如"单体应用，非高并发生产系统"）。

硬性规则：

- 数字必须来自实际运行的测试/对比，保留命令、日期与原始输出；不编造、不把单次日志写成生产指标。
- 百分比与百分点区分；"提升 X%"必须同时有基线值和新值。
- AI 完成与用户掌握分开记录，面试表述用"参与设计、实现和验证"。
- 整体结构：项目简介一段（定位 + 全链路工程优化 + 提升目标）、技术栈一行、4～5 条亮点、可选"重构/演进说明"。

## 简历亮点 v1（UPG-01 检索评测基线，2026-10-17）

> 全部数字来自 `D:/dev-learning-baselines/` 正式报告与独立复核的测试；语料为 10 条公开合成 chunk，正式"提升 X%"须等 UPG-03 生产优化后用同一管线测前后对比。

- **搭建检索评测管线，量化三路检索基线与拒答问题**：项目引入 RAG 后缺乏可信评测。建立 120 条人工标注题集（dev 40/frozen 80，含 40 条无答案题）、Recall@5/MRR@5/无答案正确率（无答案题独立统计）、5 轮测量、实验库隔离与源码快照，在独立 PostgreSQL 上测得 keyword/vector/hybrid 基线 Recall@5=`0.675/1.000/1.000`、无答案正确率=`0.900/0.000/0.000`（各 600 次）。范围：10 条合成 chunk，指标仅作后续优化的"从 X"基线。
- **通过阈值扫描定位向量拒答缺陷的取舍点**：向量检索对语料外问题不拒答（默认 `min_score=-1` 导致无答案正确率为 0，存在引导模型编造风险）。扫描 `min_score 0.2~0.8` 发现 0.5→0.6 区间无答案正确率 `0.525→0.950`、Recall@5 `0.900→0.650`，量化了召回-拒答取舍；过滤候选窗口 5/10/20/50/100 与精确 top-5 对照 overlap 与 exact match 均为 `1.0`（P50/P95≈`1.8/2.3` ms），证明小语料下窗口预过滤不丢召回。范围：单 owner/单版本合成语料；本轮未改生产默认，校准留待 UPG-03 更丰富开发集。
- **用执行计划诊断 HNSW 索引未被生产查询使用**：建了 HNSW 索引但不确定是否生效。用 EXPLAIN 计划捕获加精确/默认 planner/强制 HNSW 三路对照（确定性随机向量，100 查询×5 轮），发现 10k chunk 下默认计划不用 HNSW（P50 `29.3` ms），强制 HNSW 降至 `2.3` ms 但 top-5 重合率仅 `0.68`——量化了"索引存在≠规划器选用，强制使用存在召回代价"。范围：随机向量诊断，非真实语义语料，不构成生产优化收益。

## 简历亮点 v2（UPG-02 健身业务闭环，2026-10-18）

- **CSV 健身数据幂等导入，并发重复提交恰好写入一次**：重复上传同一份训练/体重 CSV 会产生重复场次。为导入内容生成 `sha256(owner_id+csv)` 幂等键并建立 `fitness_imports` 账本表，配合 owner+key 唯一约束与事务回滚：应用层先查账本；并发竞争下败方触发唯一键冲突，回滚整笔事务后读取胜方账本行返回"已存在"。实测：真实 PostgreSQL 上 10 轮双线程同时提交同一 CSV，每轮恰好 1 次创建、1 次幂等返回，训练场次/动作组/体重记录各恰好写入一次；API 层预览不写库、重复提交 `201→200`。范围：单库单表幂等，未覆盖分布式场景；训练量/PR/周均体重与任务完成率、时间偏差等聚合统计为正确性功能，无性能指标。

## 简历亮点 v3（UPG-03 知识库升级与正式对照，2026-10-20）

> 基线 `2026-10-17-formal-labeled-pg-v2` 与升级后 `2026-10-20-upg03-fts-or-labeled-v1` 均为正式报告：同一 120 条人工核验题集（dev 40/frozen 80，SHA-256 一致）、同一评测管线、独立 PostgreSQL/pgvector 实验库、每策略 5 轮共 600 次测量；语料为 10 条合成 chunk，不得外推为生产规模。

- **用 PostgreSQL 全文检索升级关键词召回，Recall@5 0.675→0.925，同时保持约 3× 于向量的速度**：原关键词检索在应用层对 token 交集打分，中文错位表达召回不足（基线 Recall@5=0.675，比向量低 0.325）。落库时为每个 chunk 生成受限 token 集（含重叠中文二元组），经 `to_tsvector('simple', search_tokens)` 生成列 + GIN 索引做 FTS 候选过滤，再在候选窗口内按共享 token 数确定性排序。实测 keyword Recall@5 `0.675→0.925`、MRR@5 `0.650→0.879`、P50 `3.41ms`（同轮向量 `11.39ms`、混合 `15.12ms`）；无答案正确率 `0.900→0.800`（候选变宽的代价，见下方边界）。范围：10 条合成 chunk 单 owner；计时含查询向量化+SQL+融合，不含回答模型。
- **评测管线抓回一个把关键词召回打到 0 的查询语义 bug，失败报告留档**：初版 FTS 用 `plainto_tsquery`（AND 语义），缺任一查询 token 的相关 chunk 在排序前即被截断，正式评测直接暴露 keyword Recall@5=0（同轮向量/混合不受影响，交叉印证根因在 FTS 候选层）。保留该失败报告后，改为对受限 token 构造 OR `to_tsquery`、候选窗口内确定性重排序，并新增"相关词+无关词"真实 PG 回归测试防止回退。价值：变更可量化、故障有归因、修复有回归护栏。
- **PDF 页码溯源与结构化切块**（功能正确性证据，无性能数字）：文本 PDF 经 pypdf 按页提取，切块不跨页、不跨段，页码随 chunk 落库并在检索结果中返回，回答可引用"来源+页码"；扫描件/加密 PDF 在 API 层 415 明确拒绝（暂不做 OCR）；embedding 在写事务外批量完成（`encode_many`），数据库写事务只做删旧+插入，缩短持锁时间。

## 60 秒项目介绍

这是一个学习任务助手，我把它做成了一个带 RAG 的工具调用 Agent。用户先通过 JWT 登录，Agent 收到问题后可以调用只读任务工具，或者调用 `search_knowledge` 从当前用户自己的资料中检索内容。资料使用关键词和 pgvector 混合检索，SQL 阶段会过滤 `owner_id`、`ready` 和当前 active 版本，模型回答必须引用检索来源，没有资料时要明确拒答。

创建任务属于写操作，所以模型不能直接改数据库，只能生成一个 pending proposal，用户调用确认接口后，服务端再次校验用户、状态和过期时间，再在事务中创建任务。为防止模型重复调用，我加了幂等键、工具预算、Token 预算和最大 step。系统还用 `request_id`、`agent_run_id`、`tool_call_id` 记录结构化日志，能够从一次 HTTP 请求追踪到模型和检索阶段。项目已经在 Docker Compose 中真实联调，当前定位是可演示、可排错的单体 Agent/RAG 应用，不是高并发生产系统。

## 三个核心技术难点

### 难点一：如何防止模型越权访问资料

模型只能返回：

```json
{"query": "用户问题", "limit": 3}
```

它不能生成 `owner_id`。`api.py` 通过 `current_user_id()` 从 JWT 得到可信用户身份，然后 `agent_loop.py` 调用：

```python
knowledge_executor.execute(call, owner_id=user_id)
```

`knowledge_tools.py` 再把 owner 传给检索器，关键词和向量两条 SQL 都在数据库层过滤。这样资料在进入模型前就完成隔离，不能依赖模型自觉，也不能先查出所有数据再在 Python 中过滤。

### 难点二：如何避免 Agent 写操作重复执行

`create_task` 不直接插入 `tasks`。Agent 先调用：

```python
proposal_service.propose_from_call(
    user_id,
    call,
    idempotency_key=f"{agent_run_id}:{fingerprint}",
)
```

服务端持久化 `pending proposal`。用户确认时，`TaskProposalService.confirm()` 会检查 owner、状态和过期时间，并在同一个事务中更新提案和创建任务。数据库唯一约束和条件更新共同阻止重复确认和并发覆盖。

### 难点三：如何定位一次 Agent 请求慢在哪里

API 中间件生成 `request_id`，`observability.py` 通过 `ContextVar` 将它传播到深层日志。Agent 另外记录 `agent_run_id`，模型请求记录 step 和耗时，工具记录 `tool_call_id`、候选数和耗时。

一次真实请求的证据：

```text
HTTP 总耗时：       2029.727 ms
模型 step 1：       1311.100 ms
知识检索：           15.665 ms / 8.543 ms
模型 step 2：        658.214 ms
```

因此可以判断主要瓶颈在模型调用，而不是数据库检索。

## 常见面试追问

### 为什么 `owner_id` 必须在 SQL 阶段过滤？

因为 SQL 是资料进入应用和模型之前的第一道数据边界。查询后再过滤会让不属于当前用户的资料已经进入应用内存、缓存、日志或模型上下文，存在泄露风险，也浪费数据库和网络资源。

### 为什么写操作需要 proposal？

模型输出是不可信的决策建议，不等于用户授权。proposal 把“模型想做什么”和“用户确认后实际写入”分成两个阶段，使用户能看到标题、优先级和截止日期，并让服务端在确认时重新校验身份、状态和过期时间。

### 503 和 502 在项目中如何区分？

502 表示已经向 DeepSeek 发出请求，但上游返回错误或响应结构不符合协议；503 表示本地服务暂时不可用，例如缺少 API 配置、PostgreSQL/pgvector 不可用或 Embedding 模型初始化失败。

### 为什么模型请求可以重试，而本地写操作不能随便重试？

模型 HTTP 请求失败时通常没有本地副作用，可以按错误类型有限退避重试。写操作可能已经成功提交，再次执行会重复创建任务，所以必须先有幂等机制；非幂等写入不放进普通 HTTP 重试器。

### 当前项目还有什么限制？

- 文档接口目前接收纯文本，没有 PDF/Word 解析；
- 没有异步任务队列和横向扩展；
- 评测集用于回归和策略比较，不代表大规模生产吞吐；
- 前端是原生 HTML/CSS/JavaScript 工作台，没有独立前端工程；
- PostgreSQL 有 collation version mismatch 警告，需要后续升级基础镜像或刷新数据库 collation；
- 在线模型调用依赖真实 API Key，自动化主回归使用离线替身。

## 简历亮点 v4（UPG-04 持久 Agent，2026-10-22）

以下为 AI 协助实现、可用于用户审查与讲解的候选表述，不代表用户已独立掌握全部实现。此前“无 PDF 解析”的旧边界属于原版；UPG-03 已支持文本 PDF，扫描件仍不支持。

- 为解决多轮对话丢失上下文和计划审批重启后无法继续的问题，引入 LangGraph 官方 SQLite/PostgreSQL checkpoint，配合按用户隔离的会话、消息和运行表；将周计划拆成无副作用的 interrupt 审批节点与事务 apply 节点，在真实 PostgreSQL 验证 checkpoint 重开与确认恢复，不宣称框架本身带来性能提升。
- 为防止模型越权写入和重试重复创建，模型仅调用“读取上下文 / 提议周计划 / 提议调整”工具，身份、档案 revision、计划版本与幂等键由服务端注入；确认时重新校验并整批提交。真实 PG 专项覆盖同计划双线程确认、同版本不同计划竞争、注入异常回滚和同 key 并发调整，在该测试范围内保持任务与版本一致。
- 阶段复核后补强两个数据库竞争点：同 owner/request_key 并发创建使用唯一约束、savepoint 冲突恢复及 payload hash 校验复用胜方提案；跨进程聊天完成用原子 `UPDATE ... RETURNING` 分配消息序号，并通过迁移回填既有消息最大序号。PG 同步屏障测试覆盖两种竞争。
- 建立 78 个确定性行为场景和 1 个完整性检查，覆盖身份隔离、多轮/重开会话、显式档案、计划约束、工具权限与停止边界；79 tests 通过。报告保存逐条 JUnit、源码快照与哈希、环境和命令，可区分代码回归证据与模型线上质量。
