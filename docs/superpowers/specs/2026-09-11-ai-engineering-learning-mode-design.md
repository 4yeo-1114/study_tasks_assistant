# AI 工程模式学习路线设计

> 日期：2026-09-11
>
> 适用仓库：`D:\dev-learning`
>
> 学习者：网络空间安全专业大二，每周 15～20 小时，目标为 2026 年 11～12 月开始投递 Python 后端 / Agent 应用开发实习。

## 1. 调整原因

前两周已经实现命令行任务管理、SQLite 持久化、筛选、截止日期和基础 pytest。现有进度证据显示，大部分任务的最终修复由 AI 完成，帮助等级多为 H4。继续反复手写相似 CRUD 的收益较低，但直接跳过基础又会造成“代码能运行、本人无法解释和排错”的问题。

后续改用 AI 工程模式：AI 负责大量样板代码和重复实现，学习者负责定义需求、审核代码、追踪数据流、运行验证、定位故障、解释技术选择，并完成少量能证明迁移能力的关键修改。

## 2. 目标与边界

### 目标

- 在有限时间内覆盖 Agent 应用开发所需的后端与工程基础。
- 形成一个可部署、可测试、可观测、可评测的 Agent 项目。
- 建立使用 AI Coding 仍能对代码质量和系统行为负责的能力。
- 到投递阶段能够讲清项目、定位常见故障并完成小范围现场修改。

### 不作出的承诺

学习计划不能保证录用，也不能仅凭完成任务保证“完全掌握”。能力必须由可重复的解释、排错、修改和验证证据确认。没有证据的内容保留为未验证。

### 暂缓内容

Kubernetes、复杂微服务、模型训练、推理优化、复杂多 Agent、分布式一致性深挖和完整前端体系暂缓。真实岗位描述重复要求时再提升优先级。

## 3. AI 与学习者分工

总体目标比例为 AI 完成约 70%～80% 的代码，学习者直接编写约 20%～30% 的关键代码。比例按任务性质判断，不按代码行数机械统计。

### AI 可以直接完成

- 项目脚手架、依赖配置、重复 CRUD、数据模型样板和基础测试框架。
- Docker、CI、日志配置等容易出错但重复性高的工程配置。
- 用户已经按完整清单尝试后遗留的同一轮问题。
- 文档整理、验收脚本和固定评测运行器。

AI 完成后必须说明改动、运行验证，并在学习记录中标注贡献，不能直接记为学习者独立掌握。

### 学习者必须主导

- 用自己的话定义输入、输出、异常、权限和验收标准。
- 阅读变更，沿一条真实请求解释数据流和关键调用。
- 操作程序、数据库、终端和日志，收集真实证据。
- 定位人为制造的一个故障，说明证据如何排除其他原因。
- 每个核心模块完成一个约 20～40 行或 30 分钟以内的小变式。
- 解释关键安全边界、技术取舍和已知限制。

### 自动修复规则

Agent 应在布置任务前一次列全已知问题和验收条件。学习者按清单完成并说“好了/改完了”后，Agent 一次性复核；同一轮剩余的小范围缺陷由 Agent 直接修复并完整验证，不再反复打回。新模块、新知识点或会替代核心学习目标的实现仍由学习者先尝试。

## 4. 单元学习循环

每个核心单元采用以下闭环：

1. **概念地图（20～40 分钟）**：只学当前功能必需概念，能够回答“它解决什么问题”。
2. **AI 构建（30～90 分钟）**：AI 生成或修改可运行实现，同时给出变更摘要和验证命令。
3. **代码审查（30～60 分钟）**：学习者解释入口、数据流、异常路径和依赖，不逐行背语法。
4. **故障实验（30～60 分钟）**：Agent 在测试环境制造一个典型故障，学习者用错误、日志和命令定位。
5. **关键变式（30～60 分钟）**：学习者独立完成一个小需求，可以查官方文档。
6. **证据验收（15～30 分钟）**：运行测试、口头解释并更新学习记录。

单元功能跑通但学习者尚不能解释时，功能可以标为完成，能力保持 U/C；不要求重写整个模块，而是加入复习队列，在后续相关任务中再次验证。

## 5. 掌握标准

每项技术分别记录，不能用项目整体完成替代具体能力证据。

| 层级 | 证据 | 含义 |
|---|---|---|
| L0 接触 | 看过或项目中存在 | 不写入“掌握” |
| L1 理解 | 能画出或口述数据流，解释核心概念 | 可在提示下工作 |
| L2 操作 | 能运行、观察数据库/网络/日志并复现结果 | 具备基础使用能力 |
| L3 排错 | 能根据证据定位一个典型故障 | 具备开发协作能力 |
| L4 修改 | 能独立完成小变式并验证回归 | 可记为当前阶段掌握 |

Agent 开发核心项至少达到 L3，其中 Python 基础、HTTP API、SQL、Git、测试、工具调用必须至少各有一项 L4 证据。算法以能完成常见基础题和解释复杂度为目标，不要求覆盖竞赛难度。

## 6. 后续技术栈

### 必须覆盖

1. **Python 工程**：模块、类型、异常、虚拟环境、依赖、日志、文件路径、async/await、超时和并发限制。
2. **HTTP 与后端**：FastAPI、请求与响应、状态码、校验、依赖注入、分页、认证与授权、CORS 基础。
3. **数据库**：SQL、JOIN、事务、索引、PostgreSQL、ORM、迁移、连接生命周期。
4. **工程工具**：Git 分支与 diff、Linux/SSH、Docker/Compose、环境变量、pytest、集成测试、基础 CI。
5. **联调排错**：localhost/监听地址、端口映射、DNS、连接拒绝与超时、应用日志、数据库连接错误。
6. **LLM 应用**：模型 API、结构化输出、工具调用、提示与上下文、流式输出、token/延迟/费用。
7. **Agent 工程**：执行循环、状态、停止条件、有限重试、幂等、人工确认、权限边界、运行记录。
8. **RAG 基础**：文档切分、embedding、检索、向量存储、引用、无答案处理，以及关键词基线比较。
9. **评测与可观测性**：固定用例、结果判定、失败分类、耗时与成本记录、日志和调用轨迹。
10. **安全**：输入校验、用户隔离、密钥管理、工具最小权限、提示注入与不可信检索内容边界。

### 后续按岗位补充

MCP、Redis/任务队列、WebSocket、云平台、Agent 编排框架和多 Agent。在核心闭环完成或目标岗位明确要求时加入。

## 7. 加速时间线

每周按 17 小时基准分配：项目与 AI 代码审查 7 小时，概念和官方文档 3 小时，故障实验与测试 3 小时，SQL/数据结构 2 小时，复盘与求职准备 2 小时。进入 11 月后，从项目时间中划出 2～3 小时投递和模拟面试。

| 阶段 | 建议时间 | 交付和验收重点 |
|---|---|---|
| FastAPI 与 HTTP | 09/11～09/20 | 将现有任务系统做成 API；能解释一次请求，定位 404/422/500 |
| PostgreSQL、ORM 与权限 | 09/21～10/04 | 数据库迁移、多用户隔离、事务；能写和解释关键 SQL |
| Linux、Docker、CI 与联调 | 10/05～10/15 | 可复现启动；能定位端口、配置和数据库连接故障 |
| 模型 API 与工具调用 | 10/16～10/27 | 结构化参数、查询/创建工具、确认写入；能解释执行循环 |
| Agent 可靠性与安全 | 10/28～11/08 | 超时、重试、停止条件、幂等、权限和审计；开始试投 |
| RAG、评测与项目打磨 | 11/09～11/25 | 关键词基线、向量检索、引用、固定评测和失败报告 |
| 投递与针对性补缺 | 11/26 起 | 简历、演示、模拟面试；按真实 JD 和反馈调整 |

日期可以因课程和考试移动，阶段门槛不因日期自动通过。

## 8. 每周最小手写量

为避免退化成只会运行 AI 代码，每周保留以下最小训练：

- 一次 20～40 行的项目变式，或同等规模的 SQL/测试修改。
- 两道基础数据结构或 SQL 练习，至少一道隔天重做。
- 一次不看 AI 总结的五分钟项目讲解。
- 一次故障定位，先写证据再看修复。

其余重复实现不以手写为目标。代码量不是评分指标，能够判断和负责系统行为才是。

## 9. 计划文件调整

用户批准本设计后，实施阶段需要：

- 修改 `AGENTS.md`：加入 AI 工程模式、一次性构建/复核、自动修复、L0～L4 验收和每周最小手写量。
- 重写 `Agent开发实习学习与求职计划_2026.md` 的后续阶段：保留前两周为历史，W3 起采用加速时间线与单元闭环。
- 更新 `学习进度.md`：W1～W2 标记为功能覆盖完成但能力仍按证据保留；当前入口改为 FastAPI/HTTP 单元。
- 保留既有学习日志，不回写或美化历史贡献。

## 10. 验收设计

调整完成应满足：

- 三份文件对 AI/学习者分工、时间线和掌握标准的描述一致。
- 后续 Agent 能从进度文件找到唯一的下一任务。
- 计划明确包含后端、工程、Agent、RAG、评测和安全，不以框架名代替能力。
- 学习者无需重复手写整个 CRUD，但每个核心技术都有解释、操作、排错和变式证据。
- 所有 AI 修改记录贡献归属，避免把项目完成度误当成个人掌握度。
